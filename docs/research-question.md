# Causpan Research Question

## Core Question

> Can kernel effects be reliably attributed to individual logical requests when concurrent requests share processes and execution threads?

## Deeper Question

> How can logical request identity be preserved across asynchronous userspace scheduling boundaries and associated with the kernel-level side effects generated by that logical execution?

## Why This Matters

Modern async servers multiplex many logical requests over a small number of OS threads:

```
RPC A ─┐
RPC B ─┼──> Tokio async runtime ──> Linux threads ──> syscalls
RPC C ─┘
```

At the application layer, A, B, and C are distinct logical requests with independent trust levels and security properties.

At the kernel layer, observability systems see:

```
PID
TID
timestamp
syscall/event type
file/network/process metadata
```

The kernel does not know which Tokio task, application request, span, or logical unit of execution caused a particular syscall. This creates an attribution gap:

```
Tokio task != Linux task_struct
logical request identity != PID/TID identity
```

## Key Distinctions

- **Linux task_struct ≠ Tokio task/future**
- **Correlation ≠ causation** (event A near event B does not mean A caused B)
- **TID ≠ RPC ID**
- **Application tracing ≠ kernel provenance**

## Adjacent Work

CamFlow, SPADE, whole-system provenance, Linux Audit, eBPF security monitoring (Tetragon, Tracee), OpenTelemetry, Dapper, distributed tracing, request-level eBPF observability, information flow control, causal graphs.

Existing systems can identify threads. The question is whether logical request identity survives asynchronous multiplexing strongly enough to provide reliable request-to-kernel causal attribution.
